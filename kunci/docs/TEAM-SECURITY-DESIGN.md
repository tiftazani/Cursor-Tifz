# Stage B team vault security design (proposal; not implemented)

**Release gate:** No team/admin UI, multi-user routes, or migration may ship until the key protocol below has a working cross-user prototype, adversarial tests, and independent cryptographic/security review. This document defines intended behavior, not an assertion that the current app supports teams.

## Current boundary and migration premise

The current Worker (`worker/index.ts`) routes every request through one Durable Object named `kunci` (lines 263–271). `KunciStore` has generic `get`/`set` storage operations (lines 26–48). `/api/vault` reads/writes the single `vault` key after `sessionEmail` (lines 390–401); the latter accepts a signed bearer or cookie but only the hard-coded `ALLOWED_EMAIL` (lines 167–180). OTP is sent to that address and session issuance is 12 hours; this is **not** team identity. The Worker sanitizes one PBKDF2/AES encrypted blob (`v` 1/2, `salt`, `iv`, `data`, optional wraps) and rejects some plaintext key fields (lines 228–260), but does not authenticate a per-vault writer, isolate users, compare revisions, or enforce grants. Local client sync chooses by `savedAt`, not a server CAS revision (`src/state/VaultContext.tsx` around 145–160). The recovery-mail route accepts a recovery key in plaintext to email it (Worker lines 374–387): this existing personal flow must never be used for a team vault key. Treat this as a known confidentiality exception to review separately, not as precedent.

Keep legacy personal storage and routes isolated during migration. Never reinterpret an existing personal blob as a team vault, silently copy its plaintext into a shared vault, or reuse its DEK as a team key. A deliberate, unlocked client export/import creates a new independently keyed team vault, with an explicit item selection, recipient/permission preview and confirmation. Old clients continue to see only the personal vault; fail closed on unknown protocol versions. No migration deletion until a verified round-trip on a second authorized device; allow rollback to the untouched personal blob. Never automatically merge by timestamps across the two namespaces.

## Threat model and guarantees

Assets: credential plaintext, vault DEK, private identity keys, ciphertext integrity, membership and revision state, invitation identity, metadata (members, roles, timing, size), and availability. Adversaries include another authenticated tenant/user, a revoked or demoted member with stale devices and cached keys, a compromised client/session, a malicious inviter or substituted public key, network attacker, replay/racing writers, and a curious or compromised Worker/storage operator. TLS and authenticated browser code are assumptions, not protections against a compromised origin/XSS or malicious extension. Availability, member identities, grant graph and traffic metadata are visible to the service. The service must not receive plaintext secrets or private vault/identity keys. A compromised endpoint or previously authorized recipient can copy plaintext permanently; cryptographic revocation cannot erase downloaded data. A malicious authorized writer can exfiltrate or corrupt content while authorized; signed operations provide attribution only if signing keys and clients remain trustworthy.

Distinguish account authentication (session proves immutable `userId`) from cryptographic identity (verified, device-bound public key and possession of private key). Email OTP alone does not authenticate an encryption public key. Separate owner/admin/editor/viewer permissions; server authorization constrains reads/writes, while key possession constrains decryption. Neither layer substitutes for the other.

## Keys, envelopes, and identity

Generate a random 256-bit vault DEK on an unlocked trusted client for each team vault and epoch. Encrypt the entire team vault blob client-side with AEAD (AES-256-GCM or reviewed equivalent), fresh random nonce per write, authenticated associated data binding `protocolVersion`, `vaultId`, `epoch`, `revision` and content type. Never derive the DEK from an email, OTP, server secret, team name, or personal-vault password. Use reviewed HPKE (fixed suite and test vectors chosen before implementation) to wrap the DEK separately to each authorized **device** encryption public key. Envelope AAD/context binds vault ID, epoch, recipient immutable user/device IDs, public-key fingerprint, grant generation, suite and purpose; validate all fields before unwrap. Avoid one shared group private key and avoid exposing a DEK in an API response outside an envelope. Private device keys are generated and retained client-side, encrypted at rest with a reviewed unlock mechanism; loss/recovery, multi-device enrollment, and key rotation require an explicit design before launch. Signing keys are separate from encryption keys; every membership/key transition is signed by an authorized administrator over canonical bytes including expected revision, epoch and membership digest. Clients verify signatures and an authenticated, monotonic membership checkpoint before trusting envelopes; the server enforces the same authority and CAS. A server that can equivocate about membership needs a transparency/checkpoint or out-of-band comparison design; do not claim protection from a fully malicious server without one.

An invitation names an immutable recipient account ID and verified device-key fingerprints, not merely a mutable email string. Recipient enrollment requires a fresh proof of possession for each device key bound to authenticated account ID. Before releasing any envelope, inviter and recipient verify the intended identity and key fingerprints through an authenticated out-of-band channel (or independently reviewed equivalent directory with key-change alerts). Display human-readable identity, stable ID and fingerprint; unexpected replacement/mismatch blocks acceptance. A link/OTP by itself is not key verification. Invitations are scoped, single-use, expiring, nonce-bound, rate-limited; accepting one must not silently grant access to later-added devices. Key additions/removals demand owner/admin approval and visible audit events. Define account recovery without server-held decryption escrow before implementation.

## Groups and grants

Groups are server-side policy principals (`groupId`, members, role, generation), never cryptographic identities. Effective access is the union of active direct and group grants evaluated from one committed membership revision; deny access by default. Roles: owner manages ownership and all grants; admin manages members/keys but cannot remove last owner or bypass owner transfer policy; editor reads/writes content; viewer reads only. Exactly which role may invite/rotate must be frozen in the reviewed policy matrix. No nested groups initially. A group grant must materialize/refresh per-device DEK envelopes for every eligible member; deleting a group or removing a member eliminates their *future* authorized envelopes and triggers rotation. The API must never expose other vaults' ciphertext, envelopes, or membership through guessing IDs, logs, pagination, or timing-dependent errors. Hide sensitive personal identifiers where possible; metadata remains exposed to authorized admins and the service.

## Atomic rotation and revocation

Every read and write uses server-controlled monotonically increasing `revision` and `epoch`; client `savedAt` is informational only. Membership change, group change, device removal, role reduction, key compromise, and invitation acceptance affecting access are transactional state transitions in one vault's strongly consistent Durable Object. To revoke, an authorized remaining client fetches the latest ciphertext, decrypts it, generates a **new random DEK**, re-encrypts *all* content with a fresh nonce and incremented epoch, constructs envelopes only for still-authorized devices, signs the complete proposed membership/grant/envelope/ciphertext manifest, then submits one `If-Match` revision operation. Server validates signature, authorization against the pre-state, membership and envelope recipient equality, size/schema, epoch increment, and CAS; commits the complete new manifest and ciphertext atomically or commits nothing. During preparation put the vault in a server-enforced rotation lock: do not serve old-epoch ciphertext/envelopes to newly revoked principals and reject all stale-epoch writes. If rotation cannot complete, keep access suspended for affected principals and expose a recoverable pending state, never report revocation complete. Concurrent edits/rotations return 409 and require decrypt/rebase/re-encrypt against the latest committed revision; no last-writer-wins or resurrection of old envelopes. On commit invalidate sessions' authorization caches and require fresh grant checks on every request; stale offline clients must not upload old epoch data. Consider malicious authorized clients retaining DEK and using another still-valid account/device: endpoint compromise remains out of scope for cryptographic revocation.

**Downloaded-data caveat:** prior ciphertext, DEKs, plaintext, exports, screenshots and backups cannot be clawed back. Rotation protects only future writes from a formerly authorized party (assuming new DEK remains secret). UI/API must say this plainly, including when an account is removed. If no trustworthy remaining unlocked device can decrypt/re-encrypt, rotation cannot be completed; freeze the vault and present recovery/irrecoverability rather than removing an envelope alone and claiming success.

## Proposed API and storage contract (versioned; none exists today)

All `/api/v2/*` routes require a fresh authenticated immutable `userId`, CSRF protection for cookie writes, bounded body sizes, rate limits, origin checks and server-side policy checks. Mutations require `Idempotency-Key`, `If-Match: <revision>`, canonical signed payloads and a stable audit event. Return 401 for missing auth, 403 for disallowed action (or uniform 404 for inaccessible IDs), 409 with current revision for conflict, 412 for stale precondition, and 422 for malformed protocol; never return private key material or raw exception text.

- `POST /api/v2/devices`: register public encryption/signing keys with possession proof; `GET /api/v2/devices`, `POST /api/v2/devices/{id}/replace` require verified key-change ceremony.
- `POST /api/v2/vaults`: create encrypted manifest at revision 1/epoch 1 with owner and envelope; `GET /api/v2/vaults`, `GET /api/v2/vaults/{id}` return only authorized encrypted snapshots and recipient's own envelopes; `PUT /api/v2/vaults/{id}/content` is signed CAS content update at same epoch.
- `POST /api/v2/vaults/{id}/invitations`, `POST /api/v2/invitations/{id}/accept`, `DELETE /api/v2/invitations/{id}`: verified, expiring invitations; acceptance that changes key access uses the atomic manifest transition.
- `POST /api/v2/vaults/{id}/transition`: sole atomic grant/group/role/device/epoch rotation endpoint, with complete manifest and ciphertext; `GET /api/v2/vaults/{id}/events` returns authorized tamper-evident operation history/checkpoints.

Suggested per-vault Durable Object or transactional storage partition keyed by opaque `vaultId`, never client-selected storage keys. Stored record: `{schemaVersion, vaultId, revision, epoch, ciphertext:{suite,nonce,data,aadDigest}, members:[{userId,role,status}], groups:[{groupId,members,grantRole,generation}], grants:[{principalType,principalId,role}], devices:[{userId,deviceId,encryptionPublicKey,signingPublicKey,fingerprint,status}], envelopes:[{epoch,userId,deviceId,keyFingerprint,suite,encapsulatedKey,wrappedDek,grantGeneration}], pendingInvitations:[{id,recipientUserId,expiresAt,nonce,status}], membershipDigest, signedCheckpoint, auditSequence}`. Bound all array/string sizes; normalize/canonicalize IDs and reject duplicate IDs, unknown suites, stale keys, cross-vault envelopes and missing envelopes for active readers. Keep invitation tokens hashed at rest. Store ciphertext and manifest in one atomic unit; partitioned audit/checkpoint persistence must be included in the atomic transition or use an explicitly crash-safe protocol. Do not expose generic `get`/`set` storage operations to external callers.

## Verification and review gate

Before any team UI, implement an isolated protocol prototype and independent review by someone not authoring the feature (cryptography, authorization, Worker transactional behavior, browser/extension key handling). Review a written suite choice, canonical encoding, nonce strategy, key lifecycle/recovery, identity verification ceremony, threat model, and invariant table. Resolve review findings and rerun tests before enabling a feature flag; no deployment from this document alone.

Automated cross-user integration tests must use at least owner A, editor B, viewer C, outsider D, and revoked B on separate devices/accounts: D cannot enumerate/read/write/accept another's invitation; C cannot edit or change grants; B can only access explicitly granted vaults; swapped recipient key/fingerprint or email mismatch blocks an envelope; stolen invitation and replay fail; group removal and demotion trigger epoch rotation; revoked B cannot read or write after commit even with old session, envelope or cached ciphertext; concurrent writes versus revocation and two rotations yield one atomic winner, no stale blob/envelope resurrection; interruption at every transition step yields either old committed state with access suspended or complete new state; lost-device recovery never bypasses verification; old clients cannot mutate v2 vaults; legacy personal vault remains unchanged. Verify AEAD tampering/AAD substitution, nonce uniqueness, wrong vault/epoch envelope, malformed manifests, duplicate group members, last-owner removal, size limits, idempotent retry and audit consistency. Include a candid manual demonstration that B **can** read data downloaded before revocation. Run authorization tests against the actual Worker/DO implementation, not only mocked policy helpers. No claim of zero knowledge or completed revocation without passing these gates.
